# LUMEN — правила формирования и проверки каталога

**Статус:** методика подготовки. Категория 01 «Управление Люми» описана в [COMMAND_CATALOG.md](COMMAND_CATALOG.md), категория 02 — в [COMMAND_CATEGORY_02.md](COMMAND_CATEGORY_02.md); обе зафиксированы как проектные спецификации, но ещё не реализованы. Вариативность формулировок — [VOICE_VARIANTS.md](VOICE_VARIANTS.md). В этом документе нет продуктового реестра.
Цель первого релиза — детерминированный помощник **без генеративного ИИ, LLM и автогенерации действий**. Распознавание речи проектируется отдельным слоем, локальным для Desktop, насколько позволяет выбранный движок. Нынешний Web Speech API в браузерном демо не гарантирует офлайн-работу: браузер может использовать внешний сервис. Возможность полного офлайна проверим отдельно.

## Неизменяемый принцип
Текстовый ввод, кнопка и речь (после распознавания) должны поступать в один Command Engine. Он выбирает действие по явно утверждённым шаблонам, а не «угадывает» намерение или строит произвольные инструкции. Если уверенного соответствия нет — уточняет или отказывает.

### Карточка команды — форма для будущего каталога

| Поле | Что согласовываем |
|---|---|
| ID | Стабильный машинный идентификатор по схеме `module.action` |
| Название | Название для интерфейса |
| Цель | Одно конкретное проверяемое действие |
| Платформа | Web / Desktop / обе; ограничения на ОС |
| Основная фраза | Как естественно произнести |
| Допустимые варианты | Синонимы, порядок слов, сокращения |
| Параметры | Тип, допустимый диапазон, обязательность, единицы |
| Права | Требуемая системная возможность и разрешение |
| Подтверждение | Не требуется / обязательно; точный текст подтверждения |
| Побочные эффекты | Что реально изменится и можно ли откатить |
| Успешный результат | Что проверить в адаптере, прежде чем сказать «готово» |
| Ошибки и ответы | Нет доступа, несколько совпадений, нет приложения, неверный параметр и т. п. |
| Приёмочные тесты | Положительные, отрицательные, пограничные и конфликтующие фразы |
| Статус | proposed → approved → implemented → tested |

### Технический контракт (пока только схема, а НЕ утверждённая команда)

```js
{
  id: 'module.action',
  title: '...',
  capability: '...',
  confirmation: 'none', // или 'required'
  // При required обязательно confirmationText(args).
  patterns: ['основная фраза', 'вариант с {value}'],
  parameters: { value: { type: 'integer', min: 0, max: 100 } }
}
```

`parameters` на этом этапе поддерживает integer (цифрами и русскими словами 0–100), text (с ограничением длины) и enum (фиксированные алиасы). Числовые значения цифрами можно ограничить другим допустимым диапазоном. Произвольные свободные формулировки НЕ гарантируются.

## Готовность технической основы

- Нормализация регистра, пробелов, части пунктуации и буквы «ё».
- Явные шаблоны с привязкой к началу/концу фразы; проверка коллизий идентичных шаблонов при регистрации.
- Типизированные параметры; отказ на выход за пределы диапазона.
- Приоритет более конкретной совпавшей фразы; отказ при равнозначной неоднозначности.
- Проверка доступности capability, отдельно — выданного права; всё запрещено по умолчанию.
- Подтверждение потенциально опасного действия конкретной фразой, ограниченное временем; отмена/замена ожидающего действия.
- Исполнитель сообщает об успехе только после `{ ok: true, message: '...' }` от обработчика; исключение не становится успехом.
- Тестовые команды в `tests/command-engine.test.js` — **фикстуры для проверки механики**, не утверждённый голосовой каталог.
- Новый движок пока **не подключён** к интерфейсу: текущие демонстрационные команды по-прежнему в `js/commands.js`.

## Решения, которые надо принять вместе до наполнения каталога

1. Первая целевая Desktop-платформа: Windows или сразу Windows/Linux? Web остаётся демонстрацией без прав на ОС.
2. Режим активации: кнопка/горячая клавиша; локальное ключевое слово «Люми»; продолжение диалога — что включено по умолчанию?
3. Язык первой версии, варианты произношения, допустимая гибкость. При отсутствии совпадения — уточнение, но не догадка с выполнением.
4. Какие операции требуются на MVP: категории согласовываем до отдельного разбора команд.
5. Граница между обычными и рискованными действиями; нужен ли дополнительный визуальный запрос подтверждения.
6. Должны ли сценарии управлять несколькими действиями сразу; как останавливать цепочку при частичной ошибке.
7. Политика офлайна: разрешён ли Web Speech в браузерном демо, если для настоящего Desktop нужен локальный STT.
8. Что хранить локально: историю команд, настройки, сценарии; сроки и очистка.

**Контрольная точка:** спецификации категорий 01 и 02 зафиксированы. Продолжаем проектировать остальные категории, проверять конфликтующие фразы и переносить только одобренные команды в продуктовый реестр. Не объявлять проектные спецификации реализованным функционалом.
